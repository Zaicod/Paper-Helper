# 第二阶段学习：Java 管理业务，Python 执行研究

你已经会用 Spring Boot 写增删改查，这一阶段的重点是把接口变成有用户归属、有事务、可重启保存资料的业务服务。Python Agent 继续保留，第三阶段已通过独立内部服务调用接入 Java。

## 先理解当前边界

| 部分 | 当前职责 | 当前连接情况 |
|---|---|---|
| 原 React + Python 网页 | 原有资料和研究任务入口 | 继续使用原 Python 接口 |
| Java 业务服务 | 新账号、收藏夹、论文关联、个人笔记 | 独立接口，尚未接管原网页 |
| Python Agent 内核 | 检索、RAG、分析、综合、研究构思 | 保留第一阶段统一流程 |

Java 新账号与 Python 旧账号独立，旧资料没有自动导入。默认 Java 使用 H2 文件保存业务数据，重启后需重新登录；MySQL 配置使用 Redis 保存会话。Java 调用 Python 与持久化研究任务已在第三阶段实现，Vue 页面仍待接入。

先按 [Java 启动与完整请求示例](../java-backend/README.md) 跑通一次注册、收藏、笔记与双用户隔离。无需配置模型 Key，也无需为了体验 Java 业务先启动 Python。

## 按一条请求读代码

建议从“登录用户创建收藏夹”入手，然后再读添加论文。这两个路径分别覆盖用户身份和事务边界：

1. `java-backend/src/main/java/cn/paperflow/config/`：请求如何经过 Spring Security，哪些接口公开，哪些需要登录，为什么写请求需要 CSRF。
2. `java-backend/src/main/java/cn/paperflow/controller/AuthController.java`、`service/impl/AuthServiceImpl.java`：注册校验、标准化账号、BCrypt 密码、认证上下文、会话 ID 轮换，以及当前用户 ID 如何交给业务接口。
3. `java-backend/src/main/java/cn/paperflow/controller/LibraryController.java`：接收 DTO、校验输入、获取认证用户，调用业务服务。
4. `service/LibraryService.java` 与 `service/impl/LibraryServiceImpl.java`：如何使用 `收藏夹 ID + 当前用户 ID` 查询，如何组织事务，如何处理共享论文和个人关联。
5. `mapper/` 中的 SQL 与 `entity/` 中的实体：数据库查询、唯一约束、字段映射；与 Flyway SQL 对照理解表结构。
6. `java-backend/src/main/java/cn/paperflow/common/`：业务异常和输入错误如何转成安全的 HTTP 响应。
7. `java-backend/src/test/java/cn/paperflow/`：用成功与失败请求判断系统是否履行约定。

不要只记住 Controller → Service 接口 → ServiceImpl → Mapper 的顺序。阅读每一层时，回答“这一层新增了什么判断，失败时会发生什么”。

## 比普通 CRUD 多了哪些知识

**用户隔离要在查询时完成。** 收藏夹 ID 是请求参数，用户 ID 来自登录会话。后端以两者共同定位资源，即使用户猜到了别人的 ID，也不能读取或修改。不存在和不属于本人都返回 404，避免接口透露资源归属。列表、搜索、修改、删除和笔记都要遵循同样规则。

**个人数据与共享数据需要分开。** `pf_papers` 按来源及外部标识去重，`pf_collection_papers` 表达收藏关系与该收藏夹的论文笔记。两人可以收藏同一篇论文，个人笔记互不影响；移除收藏不删除共享论文。再次添加同一论文不清空笔记，用户提交的元数据也不覆盖已有共享记录。本阶段元数据来自人工输入，尚未由外部文献源核验。

**事务保证一组写入一起成功。** 添加新论文时需要保存元数据和收藏关联。如果关联写入失败，不能留下这次操作刚创建的孤立论文。服务层事务负责统一回滚；数据库外键和唯一约束负责最终一致性，并防止并发请求绕过提前检查。

**登录状态和业务资料有不同生命周期。** 资料保存在数据库，登录状态保存在会话。本地 Servlet 会话随进程结束而消失，资料仍在 H2 文件中；MySQL 模式的 Redis 会话提供另一种持久化配置。数据库有用户记录不代表浏览器已经登录。

**CSRF 与登录是两项检查。** Cookie 表示当前会话，CSRF 请求头证明写请求掌握了该会话的 token。注册和登录也需要 CSRF；成功后服务轮换会话并清除旧 token，客户端必须重新获取。缺 token 返回 403，未登录读取业务返回 401，这两种失败要分清。

**数据迁移与查询映射各司其职。** Flyway 的版本 SQL 创建 `pf_` 业务表；MyBatis Mapper 中的 SQL 读取记录并映射到普通 JavaBean。以后修改字段时增加迁移文件，并同步修改 Entity 与 Mapper，不要修改已经应用的迁移去“修复”数据库。第三阶段按你的选择替换了早期 JPA 实现。

## 用测试理解可靠性

| 关注点 | 观察什么 | 为什么需要 |
|---|---|---|
| 注册与登录 | 重复账号、错误密码、输出不含密码哈希 | 数据合法，错误信息不暴露内部细节 |
| 会话与 CSRF | 登录前后会话 ID 变化，旧 token 失效 | 理解认证生命周期 |
| 双用户隔离 | B 访问 A 的详情、修改、笔记、论文关联均失败 | 证明权限覆盖了所有资源操作 |
| 搜索与分页 | 结果只有本人的数据，页码从 0 开始 | 防止列表绕过隔离 |
| 共享论文 | 同一论文复用记录，笔记保持独立 | 理解建模与关联关系 |
| 事务回滚 | 故意触发关联写入失败，新论文也不存在 | 验证真实数据库状态，而非只检查返回码 |

运行命令在 Java README 中。H2 集成测试可以验证这些业务行为；真实 MySQL 与 Redis 仍需在对应环境单独验证。不要把模型效果或 Python 研究质量归因于 Java CRUD 测试。

本阶段已实际通过 18 项 Java 集成测试、32 项打包服务的 HTTP 检查（含一次重启），以及原 Python 的 55 项回归测试。HTTP 检查使用临时 H2 文件，覆盖重启后重新登录读取原笔记；它验证资料持久化，不代表研究任务已支持恢复。

## 保持 Agent 学习主线

这一阶段先建立用户与资料边界，下一阶段用它承接研究任务。你可以同时继续阅读 Python，而不急于把 Agent 改写成 Java：

| Java 学习内容 | 对应的 Agent 问题 |
|---|---|
| 认证用户与收藏夹归属 | 谁能提交哪些论文、谁能查看报告 |
| DTO 与输入校验 | Python 接收的研究参数是否稳定、可信 |
| 事务与任务记录 | 任务提交成功、运行成功、结果保存成功分别意味着什么 |
| 服务调用与超时 | Java 请求超时后，Python 是否仍在执行，如何避免重复任务 |
| 结构化结果 | 分析结论、证据引用和失败记录如何传回并保存 |

第三阶段的 Java → Python 研究协议已经实现：由 Java 检查归属并创建任务，Python 处理 Agent 编排并返回阶段事件和结构化结果。需要明确任务 ID、重复提交、状态、超时与失败恢复，而不是让 Java 在一个数据库事务中长时间等待模型。

继续提升 Agent 时，围绕“证据不足后补充检索”练习工具调用与 LangGraph 条件分支：明确何时检索、最多几次、何时停止、如何引用证据。用固定案例记录质量、耗时和模型调用量，与 Java 业务测试分开评估。
