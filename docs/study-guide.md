# 论文研究多 Agent 项目：逐步学习手册

这份手册面向“没有完整上手过项目，但希望用一个作品学习 Agent 开发并准备实习”的学习者。不要一次读完所有代码。每一阶段都遵循同一个循环：先运行观察，再读少量代码，然后修改，最后用问题验收自己。

---

## 一、学完后你应该具备什么能力

完成本项目的基础版和练习后，你应该能够：

1. 区分模型、Agent、工具、工作流、状态和记忆。
2. 把一个模糊需求拆成多个职责单一的 Agent。
3. 使用结构化输出定义 Agent 之间的数据合同。
4. 分辨何时应该使用普通代码，何时值得调用 LLM。
5. 用串行和并行组合多 Agent 工作流。
6. 为 Agent 项目编写不花 API 费用的单元测试。
7. 解释幻觉、证据追溯、失败重试、费用和评测问题。
8. 把项目继续扩展为全文 RAG、评审循环和 Web 应用。

## 二、先建立正确的 Agent 心智模型

### 2.1 LLM 不等于 Agent

一次普通 LLM 调用可以抽象为：

```text
输入文本 → 模型 → 输出文本
```

一个 Agent 更接近：

```text
目标
  ↓
模型（做判断）
  ├─ 指令：角色、边界、完成标准
  ├─ 工具：搜索、数据库、代码执行、外部 API
  ├─ 状态：已经获得哪些信息、当前到哪一步
  └─ 循环：判断下一步、执行、观察结果、继续或结束
```

Agent 的价值不是“多写一段 Prompt”，而是让模型在受控环境中使用工具、读取状态并完成多步骤目标。

### 2.2 多 Agent 也不是角色越多越好

只有当任务之间存在明显不同的目标、上下文或评价标准时，拆成多个 Agent 才有意义。本项目拆分为：

- 文献搜索工具：负责真实地访问数据源，不需要 LLM 推理。
- 文献分析员：聚焦单篇论文的信息提取。
- 文献总结员：比较多篇论文，寻找共识、差异和研究空白。
- 研究构思员：针对空白提出可检验的候选假设。
- Python 编排器：决定它们何时运行以及数据如何传递。

这里最重要的设计判断是：搜索不是 Agent。让 LLM 生成论文列表很容易得到不存在的论文；让代码调用 arXiv，才能把“论文是否真实存在”交给可信数据源。

### 2.3 本项目为什么先用代码编排

多 Agent 有两种常见控制方式：

| 控制方式 | 谁决定下一步 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 代码编排 | Python | 可预测、易测试、费用稳定 | 面对开放任务不够灵活 |
| LLM 编排 | manager Agent | 灵活，可动态选择工具或专家 | 难复现，调试和费用控制更难 |

论文助手的基础顺序很稳定，所以第一版用代码编排。等你完全理解数据流，再做 manager Agent 或 handoff，才能真正理解它们带来的收益和代价。

## 五、第 2 步：学习数据合同 `models.py`

### 5.1 阅读顺序

依次阅读：

1. `Paper`
2. `PaperAnalysis`
3. `FieldSynthesis`
4. `ResearchIdea` 与 `IdeaPortfolio`
5. `ResearchReport`

你会发现它们恰好对应工作流中逐渐丰富的状态：

```text
Paper[]
  → PaperAnalysis[]
  → FieldSynthesis
  → IdeaPortfolio
  → ResearchReport
```

### 5.2 为什么用 Pydantic

自然语言输出经常发生这些问题：字段名变化、遗漏结果、列表变成段落、ID 被改写。Pydantic 把预期输出变成可校验 Schema。模型若返回不符合结构的数据，错误会在边界上出现，而不是悄悄污染后续步骤。

这相当于传统后端中的 API DTO 或数据库 Schema：它不是“为了写类型”，而是为了让不同模块有明确合同。

### 5.3 动手任务 A：增加数据字段

给 `PaperAnalysis` 增加：

```python
datasets: list[str]
```

然后完成四处修改：

1. 分析员 Prompt 要求提取数据集；摘要未说明时返回相应提示。
2. demo 实现提供该字段。
3. Markdown 报告展示该字段。
4. 测试断言报告包含数据集部分。

这个练习会让你体验“数据合同变化如何沿系统传播”。

### 5.4 验收问题

- 为什么 Agent 之间不直接传一大段 Markdown？
- `ResearchReport` 为什么同时保存原论文和分析结果？
- Schema 能消除事实幻觉吗？

关键点：Schema 只能保证结构正确，不能保证内容真实；事实质量还需要可信工具、证据引用和评测。

## 六、第 3 步：学习工具 `search.py`

### 6.1 先看接口，再看实现

在 `protocols.py` 中，搜索能力只有一个接口：

```python
async def search(topic: str, limit: int) -> list[Paper]
```

`ArxivSearchClient` 和 `FixtureSearchClient` 都满足它。工作流只依赖这个接口，不依赖某个具体数据源。这叫依赖倒置或面向协议设计。

### 6.2 `ArxivSearchClient` 的职责

1. 校验 topic 和 limit。
2. 构造 arXiv API 参数。
3. 设置超时和 User-Agent。
4. 将 HTTP 错误转成领域可理解的 `SearchError`。
5. 解析 Atom XML。
6. 将外部字段转换为内部 `Paper`。

它不负责判断论文好不好，也不负责总结摘要。工具只处理可靠 I/O 和格式转换。

### 6.3 为什么要做外部模型到内部模型的转换

arXiv 使用 Atom XML，未来 Semantic Scholar 可能返回 JSON。若整个系统直接依赖 arXiv XML 字段，换数据源会修改所有模块。现在只需新增另一个 SearchClient，并仍然返回 `Paper`。

### 6.4 动手任务 B：增加过滤条件

给 CLI 增加 `--category cs.CL`，让搜索结果只保留指定分类。先在 `FixtureSearchClient` 上实现和测试，再接入真实 arXiv 查询。

### 6.5 验收问题

- 为什么网络超时应该变成 `SearchError`？
- Fixture 与 Mock 有什么用途？
- 什么情况下“查询改写”值得成为 Agent？

推荐回答：当用户主题模糊，需要根据语义生成多个子主题、同义词和排除词时，LLM 查询规划有价值；实际查询依然应由搜索工具执行。

## 七、第 4 步：学习 Prompt 与结构化输出

### 7.1 阅读 `prompts.py`

不要只看“你是一名……”。重点寻找四类信息：

- 任务：究竟要完成什么。
- 输入边界：模型能看到哪些材料。
- 证据规则：哪些能说，哪些不能说。
- 完成标准：输出必须满足什么条件。

一个好 Prompt 通常不是写得文学化，而是减少歧义、明确失败条件。

### 7.2 三个 Prompt 为什么不同

分析员的评价标准是“单篇证据提取是否忠实”；总结员是“跨论文关系是否正确”；构思员是“想法是否针对空白、可检验、可评估”。如果合并为一个 Agent，这三套标准会互相干扰，也难以定位错误。

### 7.3 防幻觉并不只靠一句“不要幻觉”

本项目同时用了多层约束：

1. 数据源层：论文来自 arXiv，而不是模型记忆。
2. 输入层：明确只提供标题和摘要。
3. Prompt 层：未说明的内容必须标记未知。
4. Schema 层：证据说明和相关论文 ID 是必填字段。
5. 报告层：显式显示证据边界。
6. 人工层：创新想法只称候选，不宣称全新。

可靠性通常来自系统设计，不是一句神奇提示词。

### 7.4 动手任务 C：构造反例

把一篇示例摘要改成只写研究目标、不写结果。观察 demo，然后在 live 模式下观察分析员是否会编造指标。若会，改进 Prompt，并把这个输入保存成评测样例。

### 7.5 验收问题

- Prompt 和 Pydantic Schema 分别约束什么？
- 为什么构思员不能宣称“这是全新方法”？
- 为什么结果字段中允许“摘要未说明”？

## 八、第 5 步：学习模型适配与真实 Agent

先阅读 `providers.py`，理解 Qwen 如何通过 `AsyncOpenAI` 客户端的 `base_url` 接入，再阅读 `agent_team.py`。

### 8.1 Agent 的三个主要组成部分

以分析员为例：

```python
Agent(
    name="文献分析员",
    instructions=ANALYST_INSTRUCTIONS,
    model=model,
    output_type=PaperAnalysis,
)
```

- `name`：在 Trace 和多 Agent 系统中标识角色。
- `instructions`：角色、边界和行为规则。
- `model`：执行推理的模型。
- `output_type`：结构化输出合同。

`Runner.run(...)` 负责运行 Agent 循环，并在完成时返回 `final_output`。

### 8.2 为什么 Agent 定义不直接搜索

基础版选择固定工作流：Python 先搜索，再逐篇传给分析员。这样搜索词、论文数量和错误路径可预测。后续如果引入查询规划 Agent，可以把搜索函数包装成 function tool，让规划 Agent 多轮调用。

### 8.3 为什么三个 Agent 共享模型配置

这是最小可用设计，配置简单。但生产版本未必如此：

- 分析大量摘要可以使用低成本模型。
- 跨文献复杂综合可以使用更强模型。
- 想法评审可能需要独立模型降低同源偏差。

### 8.4 动手任务 D：为不同角色选择模型

让构造函数接受 `analyst_model`、`synthesis_model`、`ideator_model`。运行同一批输入，比较质量、延迟和 token 使用。这是非常适合作品集展示的实验。

### 8.5 验收问题

- Agent 与 `Runner` 各自负责什么？
- `final_output` 为什么能成为 `PaperAnalysis` 对象？
- 何时使用 Agent as tool，何时使用 handoff？

简化理解：manager 仍需汇总结果时使用 Agent as tool；希望专家接管后续对话时使用 handoff。本项目暂时都不需要，因为代码顺序更清楚。

## 九、第 6 步：学习多 Agent 编排 `workflow.py`

### 9.1 先画依赖图

```text
搜索
  ├─ 分析论文 A ─┐
  ├─ 分析论文 B ─┼─ 总结 ─ 构思
  └─ 分析论文 C ─┘
```

判断并行的规则很简单：若两个任务不读取对方的结果，就可能并行。单篇分析彼此独立；总结依赖全部分析；构思依赖总结。

### 9.2 `asyncio.gather` 的意义

LLM 和网络调用多数时间在等待响应。并行发起三篇分析通常能降低总墙钟时间。`gather` 还会保留输入顺序，因此分析结果仍与论文顺序对应。

### 9.3 为什么还需要 Semaphore

无限并发会触发 API 速率限制、放大费用峰值，也可能让错误更难恢复。Semaphore 把“可以并行”变成“最多并行 N 个”。这是 Agent 工程中很实际的资源控制。

### 9.4 当前失败策略的不足

基础版中，只要一篇分析失败，`gather` 就让整个运行失败。这对学习很直观，但生产环境需要：

- 指数退避重试。
- 区分可重试错误与永久错误。
- 单篇失败隔离。
- 保存已经成功的中间结果。
- 允许从断点恢复。

### 9.5 动手任务 E：实现失败隔离

设计一个 `AnalysisFailure` 模型，记录 paper_id、错误类型和重试次数。让 5 篇中 1 篇失败时，仍可基于 4 篇生成报告，但在报告顶部醒目标注覆盖不完整。

### 9.6 验收问题

- 为什么逐篇分析可并行，而总结不能提前开始？
- 并发越大越好吗？
- 如果总结 Agent 失败，应该重跑搜索和全部分析吗？

推荐答案：不应该；应从持久化的分析结果恢复，只重试失败阶段。

## 十、第 7 步：学习依赖注入、CLI 与报告

### 10.1 `cli.py` 是装配层

CLI 根据 mode 选择具体实现：

```text
demo → FixtureSearchClient + DemoResearchTeam
```

## 十一、第 8 步：学习测试

运行：

```powershell
pytest -q
```

### 11.1 三类现有测试

- `test_search.py`：验证外部 XML 能正确转换成 `Paper`。
- `test_workflow.py`：验证状态按预期流过整个工作流。
- `test_report.py`：验证用户可见报告包含关键章节和来源 ID。

这些测试不访问网络、不调用模型，因而快速、稳定、免费。

### 11.2 Agent 项目需要分层评测

传统单元测试只能覆盖确定性逻辑。完整质量还需要：

| 层级 | 示例指标 |
| --- | --- |
| 搜索 | Recall@K、重复率、主题相关性 |
| 分析 | 字段准确率、事实一致性、遗漏率 |
| 总结 | 证据覆盖率、跨论文归因正确率 |
| 构思 | 针对性、可行性、可检验性、潜在新颖性 |
| 系统 | 成功率、P95 延迟、token、单次费用 |

### 11.3 动手任务 G：建立第一个评测集

人工选择 5 篇你熟悉的论文，为每篇写出研究问题、方法和主要结果的参考答案。保存为 JSON。运行分析 Agent 后，先人工评分，再尝试用 evaluator Agent 辅助评分。不要只用另一个模型的分数作为唯一真值。

### 11.4 验收问题

- 为什么在线模型测试不应取代单元测试？
- LLM-as-a-judge 有什么偏差风险？

## 十二、第 9 步：运行真实版本

### 12.1 设置环境变量

```powershell
$env:DASHSCOPE_API_KEY="你的百炼 API Key"
paper-agent run --topic "multi-agent reinforcement learning" --mode live --provider qwen --model qwen3.8-flash --limit 3
```

不要把 Key 写进代码、README 或提交到 Git。`.gitignore` 已忽略 `.env`，但当前项目直接读取系统环境变量。使用百炼免费额度时还应在控制台开启“免费额度用完即停”。

### 12.2 第一次只运行 3 篇

先用小数据检查：

- 搜索结果是否相关。
- 分析是否超出摘要证据。
- 总结是否把一篇论文的观点误写为共识。
- 创意是否明确对应研究空白。
- 输出中的 paper_id 是否可追溯。

### 12.3 学会看 Trace

OpenAI Agents SDK 提供 Trace，用于查看每次运行中的模型调用、工具调用和 Agent 步骤。第一次看 Trace 时记录：每个 Agent 的输入有多大、调用用了多久、哪一步输出最不稳定。Trace 是调试证据，不只是漂亮的流程图。

### 12.4 成本意识

若搜索 N 篇论文，基础版大约发生：

```text
N 次分析 + 1 次总结 + 1 次构思
```

所以论文数量线性增加分析调用，同时让总结输入变长。后续读全文时，不能把所有 PDF 一次塞给总结 Agent，需要检索、分块、分层摘要和缓存。

## 十三、第 10 步：从摘要版升级到全文 RAG

推荐严格按顺序实现：

1. 下载 PDF，并保存原始文件哈希。
2. 提取文本，保留页码和章节标题。
3. 清理页眉页脚、断行和参考文献噪声。
4. 按章节优先、token 长度兜底进行切块。
5. 为 chunk 生成 embedding 并写入向量库。
6. 针对“方法、创新、结果、局限”分别检索证据。
7. 分析员只读取召回片段并输出引用页码。
8. 验证引用文本确实支持结论。

关键数据结构应增加：

```python
class EvidenceChunk(BaseModel):
    paper_id: str
    page: int
    section: str | None
    text: str
```

每一个重要结论不再只关联 `paper_id`，还应关联具体 `EvidenceChunk`。

## 十四、第 11 步：加入评审循环

完整流程可以演进为：

```text
分析员 → 评审员 → 是否通过？
                   ├─ 是 → 总结
                   └─ 否 → 携反馈重写（最多 2 次）
```

评审员检查：

- 每个结论是否有证据。
- 是否混淆论文之间的归因。
- 是否把“摘要未说明”擅自补全。
- 是否遗漏必要字段。

必须设置最大循环次数，否则 evaluator-optimizer 模式可能无限运行并持续产生费用。

## 十六、面试中高频问题与回答框架

### 为什么要多 Agent，而不是一个大 Prompt？

不同步骤的输入范围和评价标准不同。单篇提取要求忠实，跨篇总结要求比较，创新构思要求可检验。拆分后可分别优化 Prompt、选择模型、测试和重试；代价是调用次数和编排复杂度增加。

### 为什么搜索是工具，不是 Agent？

搜索的事实来源应是数据库。LLM 可以规划查询，但不应该生成论文事实。工具提供确定性 I/O，Agent 负责语义判断。

### 如何减少幻觉？

使用可信检索、限制输入边界、结构化输出、强制证据 ID/页码、区分未知与推断、加入评审和人工评测。不能只依赖“不要幻觉”的 Prompt。

### 如何控制费用和延迟？

限制论文数与并发；对摘要分析使用成本较低模型；缓存检索和单篇分析；只重试失败阶段；总结前压缩中间表示；记录 token、延迟和失败率。

### 你的系统如何评估？

分层评估检索相关性、单篇字段准确率、引用忠实度、跨论文归因、想法的针对性与可检验性，同时记录系统成功率、延迟和费用。

### 创新想法真的创新吗？

当前只是基于有限文献的候选假设，不能保证新颖性。需要扩大检索范围、做相似工作检查，并由领域专家验证。这种边界说明比夸大模型能力更专业。

## 十七、常见错误与排查顺序

### `ModuleNotFoundError`

确认激活 `.venv`，并执行过：

```powershell
python -m pip install -e ".[dev]"
```

### live 模式提示缺少 Key

在当前 PowerShell 会话设置 `OPENAI_API_KEY`，不要只写入一个项目没有加载的 `.env` 文件。

### arXiv 无结果

先缩短并英文化 topic，再检查网络、超时与 arXiv 服务状态。搜索失败和模型失败应分开排查。

若 arXiv 连接超时，直接切换到独立的 OpenAlex 文献源：

```powershell
paper-agent run --topic "你的主题" --mode live --provider qwen --source openalex --limit 3
```

不指定 `--source` 时默认为 `auto`，arXiv 失败后会自动回退到 OpenAlex。

### 结构化输出验证失败

查看 Trace 中模型原始输出；确认 Prompt 与 Pydantic 字段含义一致；不要第一反应就放弃 Schema 改回自由文本。

### 报告内容很空

先看原摘要是否本来就缺信息，再判断搜索相关性和分析 Prompt。不要让下游 Agent 用猜测填补上游数据质量问题。
